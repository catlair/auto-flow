# Auto Flow 文档系统

本目录是 Auto Flow 的**功能模块文档系统**：一个功能模块一份文档，记录它的
计划、实现要点、完成情况与验收记录，让任何人（包括 AI 协作者）在不读代码的
情况下快速回答三个问题——**做了什么、做到什么程度、怎么验收的**。

## 目录结构

```
docs/
├── README.md              # 本文件：规范与索引
├── STATUS.md              # 全模块状态总览矩阵（一眼看清全局）
├── architecture.md        # 系统架构总览（进程模型 / 通信 / 目录）
├── 权限引导.md             # macOS 权限引导（用户视角的操作说明）
├── 迁移计划书-*.md        # 历史里程碑文档（只读，不再更新）
└── modules/               # 功能模块文档（一模块一文件）
    ├── _template.md       # 模块文档模板（新建模块从这里复制）
    ├── recorder.md        # 键鼠录制
    ├── player.md          # 回放引擎（插值轨迹）
    ├── executor.md        # 工作流执行器
    ├── nodes.md           # 节点体系（九种内置节点）
    ├── vision.md          # 图像匹配 / OCR / YOLO
    ├── hotkeys.md         # 全局热键 / 按键捕获 / 取点
    ├── schedule.md        # 定时运行
    ├── permissions.md     # macOS 权限
    ├── rpc-protocol.md    # RPC 协议（方法与通知清单）
    ├── frontend.md        # Tauri 前端界面
    └── packaging.md       # 打包 / 签名 / 部署
```

## 模块文档规范

每个 `modules/*.md` 一律使用 `_template.md` 的结构：

1. **头部**：模块名、状态徽标、负责范围一句话
2. **代码位置**：真实路径清单（可点击级别）
3. **功能清单**：`F-<模块前缀>-<序号>` 编号，每条带 状态 / 验收标准 / 验收记录
4. **设计要点**：为什么这么实现（尤其是踩坑后反推的约束）
5. **已知问题**：诚实列出，不装完美
6. **变更记录**：日期 + 一句话

## 状态定义

| 徽标 | 状态 | 含义 |
| --- | --- | --- |
| ✅ | 已完成 | 功能可用且**有验收记录**（测试或真机验证） |
| 🚧 | 进行中 | 已开工，验收未通过或未做 |
| 📋 | 计划 | 已列入计划，未开工 |
| ⛔ | 废弃 | 已删除或被取代（保留记录供考古） |

## 维护规则

- **验收 = 可复现的证据**：pytest 用例名 / 真机操作步骤 + 观察结果 / 日志证据。
  「感觉可以了」不算验收。写进验收记录的必须能被第三人重复。
- **代码改动影响某模块行为时，同一次提交必须更新对应模块文档**（功能清单状态、
  已知问题、变更记录），与代码同行。
- 新增功能模块：复制 `_template.md` 改名，登记进本 README 与 `STATUS.md`。
- 里程碑类长文档（如迁移计划书）完成后归档只读，其结论沉淀进各模块文档。
