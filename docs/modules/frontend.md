# 前端界面（Tauri + Vue 3 + TDesign）

> 状态：✅
> 一句话：画布主导的主界面——流程图画布占满主区，参数 / 运行 / 录制收进右侧
> 可拖宽可折叠的标签侧栏。

## 代码位置

- `tauri/src/App.vue` — 布局（header + 画布主区 + 右侧标签侧栏 + 底部状态栏）
- `tauri/src/components/` — FlowCanvas / ParamsPanel / RunPanel / RecordPanel /
  WorkflowMenu / WorkflowLibDialog / PermissionBanner / ScheduleDialog /
  DiagnosticsPanel（9 个）
- `tauri/src/flow/workflow.ts` — 工作流库在界面上的纯逻辑（显示名 / 时间戳格式化 /
  导出文件名清洗 / 列表数据兜底）；无 Vue 依赖，可直接测
- `tauri/src/utils/confirm.ts` — `confirmDanger()`：统一走 TDesign
  `DialogPlugin.confirm`（**代码里禁用 `window.confirm`**，理由见设计要点 15；
  有全仓回归断言兜着：`tests/dialog-guard.test.mjs`）
- `tauri/src/flow/sidebar.ts` — 侧栏状态（宽度钳制 / `localStorage` 存取 /
  拖拽换算 / 选中节点后跳页）；纯逻辑、无 Vue 依赖，可直接测
- `tauri/src/flow/ports.ts` — 出口名与「某类节点有几个出口」（与后端逐字对齐）+
  `liveEdges`（「哪些边算数」的唯一判断：画布渲染与环检测共用）
- `tauri/src/flow/cycle.ts` — 环检测纯模块（`pathTo` 可达路径 / `cycleEdges` 刚连出的
  那个环 / `edgesOnCycles` 整张图上所有环的边），
  无 Vue/DOM 依赖
- `tauri/src/flow/summary.ts` — 节点卡片上那行参数摘要
- `tauri/src/flow/duration.ts` — 时长/时刻的换算与清洗（面板、摘要、录制库三处共用）
- `tauri/src/flow/recording.ts` — 录制库在界面上的纯逻辑（下拉选项 / 缺失兜底 / 时长文案）
- `tauri/src/flow/fitOnce.ts` — 「首次拿到非空工作流时适应一次视野」的状态机（纯模块，可单测）
- `tauri/src/stores/app.ts` — Pinia：连接/运行/录制态、录制库列表、托盘同步、工作流镜像、全部 RPC 调用
- `tauri/src/rpc/client.ts` — NDJSON 客户端（id 配对、通知订阅、半包切分）
- `tauri/src-tauri/src/lib.rs` — Rust 外壳：sidecar 守护、**系统托盘**、窗口生命周期
  （关窗即隐藏、Dock `Reopen` 唤回）、`af_tray_state` / `af_hide_window` 两个命令

  **「图标到底在不在菜单栏」怎么验**（这题没法和别处一样靠二进制搜或截图）：

  - 二进制搜**搜不到**，而且有四种成因，别据此下结论，**搜不到 ≠ 没打包进去**：
    ① `TrayIconBuilder::with_id` 的 id、`generate_handler!` 的命令名被 LLVM 内联成立即数比较；
    ② **常量合并**——`退出 Auto Flow`、`● 开始录制`、`■ 停止录制` 在安装版里 `grep -a -c`

    ③ **`format!` 按占位符切段**——状态行在 `.rodata` 里是
    `托盘状态项 recording=` / ` 菜单文案=` / ` set_menu=` / ` set_title=` / ` set_tooltip=` / ` rect=`

    ④ 片段还会被**去重搬到别处**：` 角标=` 就在偏移 3444513 的另一处常量池里（旁边是
    `set_text` / `rpc_down` 这些），与同一条 `format!` 的其它片段不连续。
  - 截图**不可靠**：显示器休眠时 `screencapture` 全黑 / `could not create image from rect`；
    锁屏时菜单栏只画系统那几项，第三方状态项根本不画。

    **功能的一部分**，不是调试残留：删了它，「找不到图标」就再没有现场可查。
    新增的 1 条用例就守这一点，反向验证 8 条（去掉建托盘成功日志 / `rect` 改自造坐标 /
    状态行整行删 / 缺「打算设的角标」/ 缺 `set_title` 结果 / **把结果写死成成功** /
    **非录制支不清角标** / 句柄查不到那行删掉）⇒ 各自对应的断言挂。

  | 日志片段 | 回答的问题 |
  | --- | --- |
  | `托盘已创建（…）` | 建成功才有；失败另有 `托盘创建失败：…`，两者不混 |
  | `recording={recording} 角标={badge:?}` | 前端推来的状态、我们**打算**设的角标值 |
  | `set_menu/set_title/set_tooltip={…}` | 三个调用是否成功——它们原本被 `let _ =` 吞掉，静默失败与"没设"分不开 |
  | `rect=Ok(Some(Rect {…}))` | AppKit 给出的状态项位置；`None`/`Err` = **没有**状态项 |

## 设计要点

1. **画布吃满宽度，控制面板进侧栏**（2026-09-15 改版）：原先是三栏等分，
   画布只拿到约 1/3 宽——而画布恰恰是最需要空间的那个，流程图一宽就得反复
   平移缩放，画大一点就难受。并排还有第二个代价：参数面板经常是空的，空着也得占位。
   改成「画布 `flex:1` + 右侧标签侧栏」后，画布拿到除侧栏外的全部宽度，参数面板
   独占整条高度（多路分支这类长表单不再被压成一小截滚动条）。
   - 侧栏宽度可拖（280–620px）、可整体折叠，两者与当前页签一起记进 `localStorage`
     ——这是「这台机器上怎么用」的习惯，不该每次重开都重置。
   - 三个面板用 **`v-show` 而非 `v-if`** 保持挂载：录制面板的文本草稿
     （`textDraft` / `keysToTextDraft`）与事件列表的选中项、滚动位置都是组件内状态
     （见 `RecordPanel.vue`），切一次标签就丢一次会让人白填。
   - 运行/录制状态做成页签角标（▶ / ●），在别的页签上也能一眼看到。
   - 选中节点时自动切到「参数」页——选中节点本来就是为了改它。
   - 侧栏状态的纯逻辑（钳制、存取、拖拽换算、选中后跳页）抽在
     `tauri/src/flow/sidebar.ts`，`App.vue` 只持有三个 ref：留在这里只能靠
     「手动拖一下、关掉再开一次」验证，抽出来就能直测。
2. **响应驱动刷新**：凡改变后端状态的操作，以响应中的 workflow_current 收敛
   本地镜像；`workflow.changed` 通知只作广播冗余。曾依赖通知，偶发丢失导致
   「删除不刷新」「写入节点列表不动」。
3. **通知处理隔离**：handleNotification 外层 try/catch——单条通知异常不打死
   后续通知。
4. **热键屏蔽**：输入框聚焦时忽略 hotkey.triggered（用户在打字时 F10 不应抢焦点）。
5. **事件流性能**：5000 条截断 + 仅渲染最近 200 条 + 录制事件 100ms 批量推送。
6. **后端告警要能被用户看见**（F-UI-13）：后端（尤其 `core.vision`）的 WARNING 只进
   `~/Library/Logs/autoflow-tauri.log`，那份日志是逐帧 RPC 收发记录、不含诊断字符串，
   用户「为什么没匹配上」只能自己翻日志。现由后端 `log.warning` 通知送来，
   前端存 `backendNotes` 并**同时**做两件事：诊断面板成块显示（可整段复制），
   以及**仅在当前无横幅时**弹一条 warn 横幅——已有 error 横幅时不能覆盖
   （告警是补充信息，不是更高优先级）。
   注意 `log.warning` 是可丢类通知（见 rpc-protocol.md 设计要点 4），
   所以它**只能**作为「锦上添花」的诊断线索，前端不得依赖它收敛任何状态。
7. **画布是「投影」，不是第二份真源**（F-UI-02）。`vNodes` / `vEdges` 两个 computed
   把 store 里的工作流投影成画布要的形状，任何交互都发 RPC、等响应回来再刷新，
   **不做乐观修改**——乐观改边之后如果后端拒绝（自环、节点已删），画布会停在和
   后端不一致的状态。
   两个必须的实现细节：
   - **每次投影都重建新对象**。Vue Flow 会往收到的节点上挂 `dimensions` /
     `selected` / `handleBounds` 等字段，直接传 store 里的对象等于让库改真源。
   - **手柄锚在「最近的定位祖先」上，所以定位元素的选择就是手柄的落点**。库自带的
     `.vue-flow__handle-right` 是 `top:50%; right:0; translate(50%,-50%)`，
     `top:50%` 相对**最近的定位祖先**解析。三种手柄各有各的锚：
     - `.af-gnode`（卡片本体）——单出口手柄、以及左/上/下三个目标手柄的锚。
       不写的话它们会一路锚到 `.vue-flow__node` 上，位置随库的节点容器走。
     - `.af-exit`（出口行）——**必须**是定位元素。多出口时每个手柄锚在自己那一行上，
       才落在各行的中线上。
     ⚠️ **`.af-exit` 少了 `position: relative` 会让多出口的手柄全部塌到卡片中线上、
       几个完全重合**：表现是四个出口只有一个圆点，而且 Vue Flow 按「离指针最近的手柄」
       判定落点、永远只命中第一个，**根本连不出「情形 2/3」**。
       2026-09-15 这里踩过一次：当时为了治「圆点压住标签最后一个字」，把
       `position: relative` 从 `.af-exit` 挪到了 `.af-gnode`——字是不压了，
       但手柄全部塌到了中线上，而且**上一轮的目视验收只核对了标签是否完整、
       没核对手柄是否落在自己那一行**，于是被误判成「已修好」。
       正确的做法是两者都要：**行保持定位**（决定纵向），**行加 `padding-right: 10px`**
       （决定横向不压字）。纵向和横向是两个独立的问题，别用一个改动同时「解决」。
     - `.af-exits` 用**负外边距** `margin: 4px -10px 0` 抵消卡片的左右内边距，
       让出口行一直延伸到卡片内沿——多出口的手柄才和单出口的落在**同一条竖线**上
       （否则会内缩 10px，同一种「出口」画在两处）。
     不用覆盖库的样式，也就不会随库升级失效。
8. **`start` 不渲染入手柄、`end` 不渲染出手柄**，所以这两类边在画布上根本连不出来。
   比「连上再报错」好：用户的意图是明确的，不该让他先犯一次错。
   自环由 `isValidConnection` 拦掉（后端也会拒，但在那里拒是「先连上再被弹回」，
   画布会闪一下）。**没有别的额外规则**——不在前端拦后端允许的东西，
   否则用户会遇到「后端接受、界面拒绝」的困惑。
9. **画布那一列自己管滚动**。`.af-flow-col` 是 `display:flex` + `overflow:hidden`，
   不能沿用 `.af-col` 的 `overflow-y:auto`：让外层滚动会把画布一起滚走，
   而画布要的是「固定大小 + 内部平移缩放」。
10. **新节点落在当前视口中心**（F-UI-02）。画布可以平移缩放，固定坐标在用户把视野
   挪走之后会落在屏幕外——表现就是「点了添加，什么都没发生」，而节点其实加上了。
   屏幕坐标 → 画布坐标 = `(屏幕中心 - 视口平移) / 缩放`，再按已有节点数错开一点，
   避免连点添加时叠成一个点。
11. **旧文件迁移提示是可关闭的、且只弹一次**（F-UI-15）。后端把 v3 的线性列表接成
    线性边链，但 `run_when` 的门控语义无法一对一映射成边，用户必须知道要去重连。
    两个细节：只在标记「从否变是」时弹（否则改个参数就会重新弹出来，等于关不掉）；
    换成非迁移工作流时撤掉（否则提示会一直说上一个工作流的事）。
12. **`fitView` 必须等 Vue Flow 量完节点尺寸**（F-UI-02，状态机在 `flow/fitOnce.ts`）。
    两个时机**不能合并**：
    - `request(hasNodes)` —— store 里有节点了（数据到位）。**这里只能标记意图。**
    - `commit()` —— 收到 `nodes-initialized`（所有节点都有非零尺寸）。**这时才 fit。**

    早先写的是「数据一到就 `nextTick(() => fitView())`」，太早：Vue Flow 还没测出
    新节点宽高，包围盒是退化的，`fitView` 等于没调；更糟的是意图已被消费，等尺寸
    真量完时反而不会补第二次——**表现是打开一份已有工作流后只看到左上角一两个节点，
    其余在视野外，用户会以为工作流是空的或者坏了**（和「迁移时不摆坐标」同类：
    画布没把人带到该看的地方）。正确信号是 `nodesInitialized`：它只在所有节点尺寸
    非零时才发；新增节点会先把它落回 false、量完再变 true，所以每次拿到新节点都能
    等到一次。适应过之后 `request` 不再生效（否则每次编辑都把用户调好的视野拉走）；
    工作流被清空时 `reset()`，让下一份重新适应。

13. **连线落点：左/上/下三边都能落，落点侧持久化**（F-UI-02）。
    原先是「目标手柄只有一个、固定在左侧」——要连一条边得从源节点右侧拖到目标
    节点左侧那个小圆点，目标在右边时还得绕过去，很不顺手。
    现在左/上/下各有一个目标手柄，**在哪儿松手线就从哪一侧画进去**。
    三个必须说清的点：
    - **为什么没有右侧**：右边是**输出侧**（出口手柄都在卡片右边缘）。单出口节点的
      出口手柄正好在右边缘中线，与右目标手柄**同点重合**——Vue Flow 按「离指针最近
      的手柄」判定落点，两点重合时谁被选中取决于距离是否严格相等，行为不稳定，
      表现是「有时连得上有时连不上」。所以入口只开放 左/上/下。
    - **为什么落点侧要持久化**（`Edge.dst_side`）：各侧手柄必须用**不同的 id**
      （Vue Flow 解析锚点走 `handles.find(h => h.id === handleId)`，同 id 只命中
      第一个）。既然各侧 id 不同，边就必须记住自己用的是哪个——否则**拖拽预览**
      连在你松手的那一侧、**落库后**却画到第一个手柄上，用户会看到连线「跳」一下。
    - **脏值必须收敛**（`normalize_target_side` / `normalizeTargetSide`）：存了词表
      以外的值，前端就找不到对应手柄，Vue Flow 直接画不出这条边（只在控制台刷告警），
      用户看到的是「连线莫名消失」——比画错一侧严重得多。
    上/下两个手柄平时淡显（`opacity: .3`）、**悬停节点或正在拖连线时变清晰**
    （`.af-gnode:hover` / `.af-connecting`）：既让人发现「这两边也能连」，
    又不至于每个节点都挂三个圆点显得乱。
    - **拖拽时必须全亮**：拖连线的时候正是用户找落点的时候，这时候还淡显等于
      「有落点却看不见」，用户会以为只能连到左边——这个功能就白加了。
      `connecting` 由 `@connect-start` / `@connect-end` 驱动（已核对 `@vue-flow/core`
      的 `emits` 里确有 `connectStart` / `connectEnd`）。
    - **不要**改成 `opacity: 0` 藏起来：虽然照样能落点（命中判定用的是
      「手柄中心点与指针的距离」，与可见性无关），但用户根本不知道可以往那儿连。

14. **连线成环要提示、把环上的边标出来，但绝不拦**（F-UI-16）。算法与
    「为什么只提示不拦」「为什么返回边而不是 `true`」的完整推理在
    [flow.md](flow.md) 设计要点 18，这里只记前端侧的实现约束：
    - **判断在 store 的 `addEdge` 里做，不在画布组件里**。`replaced` 已经在同一个
      返回值里了，两者都是「这次连线对图的影响」，分两处算会出现
      「一个说替换了、一个说成环了」的对不上。所以返回值从 `boolean` 变成
      `{replaced, cycleEdges}`，**改签名会让所有调用点编译期报错**——
      这比「悄悄少提示一句」好，故意不提供默认值。
    - **两个判断用的边表不同，不能图省事合成一个**：`replaced` 用**全部**边
      （后端按 `(src, port)` 替换时不看出口是否合法，被调小 `case_count` 后残留的
      那条同样会被顶掉，漏判会让用户以为连了两条）；环检测用**活边**
      （`liveEdges`，见设计要点 6 与 flow.md 设计要点 14）。
    - **边 id 的格式只允许定义一处**（`edgeId()`）。`vEdges` 要用它当 `id`，
      「把环上的边标红」要用它做集合查询——两处各写一遍 `${src}|${port}` 就是等着漂，
      而漂了的表现是「提示说有环、画布上却一条都没标红」，用户只会觉得提示是错的。
      用例把「只有一处」钉住了（反向验证时把字面量写回去，断言立刻点名「实际 2 处」）。
    - **高亮是纯画布视图态**（`cycleIds`），不进 store、不落盘：它是「刚才那一下」的
      反馈，不是工作流的属性。
    - **靠「下一次交互」清掉，不用定时器**（`clearCycleHighlight`，挂在
      `@connect-start` / `@node-drag-stop` / `@node-click` / `@pane-click` 四处）。
      定时器要么太短（还没看清就没了）、要么太长（挡着后面的操作），而
      「我动手了就说明我看完了」是确定的信号，也不引入可能泄漏的 `setTimeout`。
      ⚠️ 四处**缺一不可**，用例逐个 handler 检查而不是数总数——数总数的话
      删掉一处、另一处多写一遍也能凑够。
    - **视觉上不能只换颜色**：红色 + 加粗 + `animated`（库自带的虚线流动，
      `.vue-flow__edge.animated`）。一屏细线里一条静止的红线仍然可能被忽略，
      动起来才一眼能认出来。
    - **提示文案带节点名**（`nodeLabel`：自定义名优先，否则用类型名——**与卡片上
      显示的一模一样**）。只报 uid 等于让用户自己去对，节点一多就对不上了。
      注意「同名节点」不构成歧义：这里只是帮人定位，不是身份标识。
    - 用 `MessagePlugin.warning` 而不是 `error`：这不是失败，是「确认一下」。
      用 error 会让用户以为连线没成功。
    - **文案不能写「这是死循环」**：静态判定死循环是不可判定的（分支没被选中的
      `case` 上的环永远不会走到）。写了就是在无法判定的问题上给结论，
      用户一旦发现「提示了但根本没死循环」就会连真提示一起不信。
    - **常驻标环开关**（`showCycles`，默认关）：工具栏上一个 `t-button`，开启时
      文案带条数（「标出环（3）」）。算法（强连通分量）与「为什么必须真找环」的
      推理在 [flow.md](flow.md) 设计要点 19，这里只记前端侧的约束：
      - **常驻集合是 `computed`，不是一次性快照**：用户开着手动删掉一条边、环没了，
        红色要跟着没。所以它必须随 `store.workflow` 变化重算。
      - **与 `cycleIds` 分开存，不能合成一个状态**：生命周期完全不同——`cycleIds`
        是「刚才那一下」的反馈、下一次交互就清；常驻集合只要开关开着就一直在。
        `vEdges` 取**并集**，于是开关关掉后「刚连的那条环」仍然可见。
      - ⚠️ **`clearCycleHighlight()` 绝不能顺手清常驻集合**（比如顺手把 `showCycles`
        置回 `false`）。那样每次点空白红标记都消失，用户会以为开关是坏的——
        这是本功能最容易写坏的一处，有用例专门盯它，反向验证时断言点名
        「clearCycleHighlight 把常驻标环也清掉了（开关会看起来是坏的）」。
      - **关着时要短路**（`if (!showCycles.value) return new Set()`），别在没开开关的
        时候白算一遍整张图的强连通分量。
      - 它是**视图态**：不进 store、不落盘，后端完全不知道有这回事（和 `cycleIds` 一样）。
        代价是重启应用后回到默认关——对一个「看图的辅助」来说可以接受，
        要持久化就得走配置，那是另一件事。
      - 工具栏因此多了一个控件，`.af-flow-bar` 加了 `flex-wrap: wrap`：
        画布面板只有约 340px 宽，四个控件不换行会横向溢出把最后一个挤掉。
      - 高亮样式与 `cycleIds` **完全共用**（同一份 `vEdges` 投影），
        不另写一套颜色，否则两处迟早不一致。

15. **工作流库的界面只做展示，状态一律由后端给**（F-UI-20）。存储格式、
    `dirty` 的判据、未保存保护都在 [workflow-lib.md](workflow-lib.md)，
    这里只记前端侧的约束：
    - **「当前这份在不在库里」不记第二份状态**。判据只有后端返回的 `lib_id`
      （`applyLocation()`），前端**不另存**「我刚存到哪个 id」。记两份的话总有一天
      对不上，症状是「保存写进了 A 文件、界面显示已保存到 B」，**两边都不报错**。
    - **`applyLocation` 必须判 `"path" in cur`，不能判 `typeof`**。`workflow.new`
      返回的 `path` 是 `null`（新建不落盘），用 `typeof === "string"` 判会整帧跳过，
      于是新建之后「当前」徽标还挂在上一条上——这是真写坏过一次的地方。
    - **未保存标记 `●` 直接读后端的 `dirty`，前端不算账**。定时任务触发时会直接换掉
      整棵树，那条路上前端一个请求都没发过，靠前端记账必然漏。
      赋值前判 `typeof === "boolean"`：字段缺失时沿用上一次的值，用户会看到 `●`
      却怎么也存不掉。
    - **确认框统一走 `utils/confirm.ts`**（`DialogPlugin.confirm`），
      **绝不用 `window.confirm`**。后者在本项目里**拦不住任何东西**：Tauri 把它
      注入成 `async function(){ return await invoke("plugin:dialog|confirm", …) }`，
      返回 **Promise**（恒 truthy）⇒ `if (!window.confirm(...)) return;` 的 `return`
      永不执行、`&&` 形式的右侧无条件执行；而本项目没授予 `dialog:allow-confirm`
      ⇒ invoke 被权限拒绝，**连框都不弹**。也就是说它的语义是「无提示直接做」。
      调用方**必须 `await`**（不 await 等于没拦）。`settle` 要排在
      `destroy()` **前面**，否则 `onClose` 先把 promise 结算成 `false`。
    - **`-32006 unsaved_changes` 是跨语言常量**：Python 侧定义、两个 `.vue` 各写一遍。
      改一边不会编译失败，表现是「确认框不弹、直接报错」。所以有 1 条用例读
      `rpc/controller.py` 把码取出来比对。
    - **「运行」在库里那一份上要一次请求都不发**：正在运行时直接 `warning` 返回。
      先发 `open` 再发现不能跑，会把用户当前的工作流换掉——那是数据损失，
      不是提示问题。
    - **行内改名输入框用函数式 ref**（`:ref="setNameInput"`）。`ref="x"` 写在
      `v-for` 里会被收集成**数组**，`x.value.focus()` 报「focus 不是函数」。
    - **导出文件名要洗过**（`wfExportName`：`/` `:` `\` 与控制字符换下划线、
      去掉开头的点、截断 80 字）。名字是用户随便起的，含 `/` 时会被系统当路径分隔符，
      表现是「导出到桌面」却在别处冒出一个目录。
    - **时间戳格式化用字符串切片，不用 `new Date`**。后端给的是
      `"2026-09-15 11:20:33"`，这不是 ECMAScript 规定的格式，别的引擎会收成
      `Invalid Date` 显示成 `NaN-NaN-NaN`。
    - **定时任务面板的工作流字段从库里下拉选**（+「浏览…」兜底 + 库外路径项）。
      工作流进库后文件落在 `~/Library/Application Support` 下，还让用户开文件对话框
      等于让人去翻系统目录——这是工作流入库**顺带修掉的回归**（见已知问题）。

## 已知问题

- WebView 输入框无法被系统级合成键盘可靠注入（自动化测试限制，人工输入正常）。
- 断连重连后 2s 内的 UI 状态可能短暂陈旧（依赖后端重连握手重放 workflow.current）。
- workflow.changed 通知经 Tauri 事件转发偶发丢失（未定位帧级原因）——结构操作
  已全部改为响应驱动刷新，通知丢失不再影响 UI。
- **画布没有框选、复制粘贴、对齐吸附**，节点多了以后手工摆位比较累。
- **组件渲染仍然没有真正的测试覆盖**（无 WebView 环境），画布的行为最终还得靠
  真机目视。能单测的部分尽量下沉到 `src/flow/` 与 store：出口名、摘要、store 动作，
  以及 `fitOnce` 状态机；**纯 CSS 的坑**（手柄锚点）用源文件结构断言兜住——
  它不是真正的布局验证，只是「别再写回那个已知错误写法」的回归门。
- 引入 @vue-flow/core 后 bundle 从约 1.0 MB 涨到 1.63 MB（gzip 443 KB）。
  桌面应用从本地加载，可接受。
- **成环提示只在「手动连线」这条路径上**（F-UI-16）。**打开文件时不自动检查图里已有的
  环**——这是刻意的（循环合法，每次打开都告警而且关不掉，见 flow.md 设计要点 18），
  所以盲区只剩「手工改过的 json / 从别处拿到的文件」。
  这类文件要看环，得**自己点工具栏上的「标出环」**（默认关）——也就是说，
  这个能力存在但**不主动暴露**：用户不知道有这个按钮，就等于没有。
- **常驻标环开关不持久化**：它是画布组件里的视图态，重启应用回到默认关。
  想记住得走配置，那是另一件事（现在没做）。
- **标题栏里「未保存 ●」与「● 已连接」挨在一起，读起来分不清**（F-UI-20 真机目视发现）：
  未保存时整行是 `未命名工作流 ● ● 已连接 v0.1.0` —— 两个圆点相邻，颜色不同
  （橙 vs 绿）但一眼扫过去像「两个状态点」。当时把标记做成名字的一部分是为了
  避免「6 像素的点被当成渲染瑕疵」，但没预料到它会紧挨着连接状态点。
  可能的改法：把连接状态移到最右、或在未保存标记后用括号写「未保存」。
  **没改**——需要一次设计决定，不是随手能调的小事。
- **工作流库弹层没有搜索、排序选项、标签、收藏**：列表按「最近修改」倒序（后端给的
  顺序），条目多了只能自己往下翻。
- **「新建」不落盘，所以空工作流不会出现在库里**（F-UI-20 的刻意设计，理由见
  [workflow-lib.md](workflow-lib.md)）。用户新建之后直接关窗口，这份就没了——
  和「新建即入库」相比这是有意的取舍，但**界面上没有提示**。
